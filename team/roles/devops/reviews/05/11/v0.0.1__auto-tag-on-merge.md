# DevOps review - auto-tag on dev/main merges

**Version:** v0.0.1 (will become the version that triggers the first bump)
**Date:** 2026-05-11
**Supersedes:** parts of `v0.0.1__ci-pipeline-bootstrap.md` (the static `auto-tag` job)

## What changed

`.github/workflows/main.yml` no longer reads the version statically from
`sg_image_builder/version` and tags only on `main`. It now:

1. Runs on push to `main` **or** `dev`
2. Skips runs when the only paths changed are docs / scaffolding / the
   version file itself (paths-ignore list)
3. After lint + tests + zipapp build, calls the **`owasp-sbot/OSBot-GitHub-Actions/.github/actions/git__increment-tag`** composite action
4. Bumps the patch segment on `dev` (`release_type: minor` in the action's
   labelling) and the minor segment on `main` (`release_type: major`)
5. The action updates `sg_image_builder/version`, commits with
   `Update release badge and version file`, pushes the commit back to the
   branch, then pushes the new tag

## Why this action (vs. rolling our own)

The sister repo `the-cyber-boardroom/SGraph-AI__Service__Playwright`
already uses this same action across its `ci-pipeline__dev.yml` and
`ci-pipeline__main.yml`. Reusing it means:

- Battle-tested across at least one production project
- Identical behaviour - someone moving between repos finds the same workflow
- Less custom shell scripting in our YAML

The action's source lives at
`https://github.com/owasp-sbot/OSBot-GitHub-Actions/.github/actions/git__increment-tag/action.yml`
and is mirrored locally at `/home/user/_reference/OSBot-GitHub-Actions/`
for offline inspection.

## The label-inversion gotcha

The action's `release_type` values are **inverted** vs semver intuition:

| `release_type` value | What the action does           |
|----------------------|--------------------------------|
| `minor`              | bumps **patch** (X.Y.Z -> X.Y.(Z+1)) |
| `major`              | bumps **minor** (X.Y.Z -> X.(Y+1).0) |

So the user's chosen "patch on dev, minor on main" rule maps to:

| Branch | `release_type` we pass | Effect             |
|--------|------------------------|--------------------|
| `dev`  | `minor`                | v0.0.1 -> v0.0.2   |
| `main` | `major`                | v0.0.1 -> v0.1.0   |

Documented inline in `main.yml` so future readers don't get tripped up.

## Loop prevention

The action commits the version-file bump back to the branch. Without
mitigation that push would re-trigger this same workflow, which would
bump again, ad infinitum. Two protections:

1. **`paths-ignore`** on the workflow excludes `sg_image_builder/version`.
   The bump commit only changes that file, so it doesn't re-trigger.
2. Belt-and-braces: the action's commit message doesn't contain `[skip ci]`
   but the path filter is sufficient.

## Seed-tag step (first-run only)

The action calls `git describe --tags $(git rev-list --tags --max-count=1)`
to find the latest tag. If no `v*` tag exists yet, that command fails.

So `main.yml` includes a one-time **seed** step that runs **before** the
action:

- `git fetch --tags`
- if no `v*` tag exists, read `sg_image_builder/version` and tag the
  current commit with that value, push the tag
- otherwise skip

Idempotent: once any `v*` tag exists, the seed step is a no-op forever.

## First-run trajectory

Assuming the first merge into `dev` happens with `sg_image_builder/version`
at `v0.0.1`:

| Event                            | Resulting state         |
|----------------------------------|-------------------------|
| (Today) `v0.0.1` in file, no tag | nothing tagged          |
| Merge feature into `dev`         | tag `v0.0.1` seeded; then bumped to `v0.0.2`; bump commit on `dev` |
| Next merge into `dev`            | bump to `v0.0.3`        |
| ...                              | ...                     |
| Merge `dev -> main`              | bump to `v0.1.0` on `main` |

Every push of a `v*` tag separately triggers `tag.yml`, which builds the
zipapp and creates a GitHub release.

## Branch-protection considerations

This workflow pushes commits **and** tags back to `dev` and `main`. For
this to succeed, branch protection on those branches must either:

- Allow `github-actions[bot]` to bypass, **or**
- Not require pull requests for these specific commits

The user owns branch-protection setup. Worth a configuration check once
secrets are in place.

## Other path-ignores

The workflow now ignores changes that touch only docs / scaffolding:

- `**/*.md`
- `team/**`
- `humans/**`
- `docs/**`
- `library/**`
- `_vaults/**`
- `.github/**/*.md`

Rationale: a brief or a debrief doesn't warrant a release. If `team/` or
`humans/` content evolves, no CI cost. PRs that touch only those paths
still run `pr.yml`'s lint + unit + integration gates (pr.yml is
unchanged).

## Manual version overrides

If someone manually bumps `sg_image_builder/version` in a feature PR, the
action's behaviour is **to ignore the file value** and increment from the
latest **git tag**. So a manual edit would get overwritten by the
auto-bump. Recommendation: don't hand-edit the version file once
auto-tagging is live; let the tag be the source of truth.
