## What the docs actually say

The Type_Safe canon has a **strong** rule and a **soft** rule, in that order:

**Strong rule (non-negotiable):**

> NEVER use raw `str`, `int`, or `float` in Type_Safe classes. Raw primitives enable entire categories of bugs and security vulnerabilities.
>
> -- v3.63.4 §"Critical Principle: Ban Raw Primitives"

**Soft rule (judgement call, this is where the calibration lives):**

> Choose the right primitive: Use domain-specific types (Safe_Str__Email, Safe_UInt__Port) over generic ones
>
> -- v3.28.0 §"Best Practices" #1

The strong rule is what the dev pack §10 was channelling. The soft rule
is what Dinis was flagging: **don't invent a custom `Safe_Str__Image_Builder` /
`Safe_Str__Provider_Name` / `Safe_Str__Spec_Id` for every domain concept
just because you can.** The OSBot library already ships 100+ primitives,
and Type_Safe also accepts plain `Safe_Str` / `Safe_Int` / `Safe_UInt` /
`Safe_Float` as the "no special validation needed" types - and that's
fine when no special validation is needed.

## The calibrated rule for this repo

A four-level ladder, climb only as far as you need:

| Level | When to use it | Examples in M1 |
|-------|---------------|----------------|
| **0. Built-in `bool`** | Booleans never need wrapping | `enabled: bool`, `force: bool` |
| **1. Existing OSBot domain primitive** | An existing type matches the constraint exactly | `Safe_Str__Url`, `Safe_Str__File__Path`, `Safe_Str__Slug`, `Safe_Str__Version`, `Safe_UInt__Port`, `Safe_Float__Percentage_Exact`, `Safe_Id`, `Random_Guid`, `Timestamp_Now` |
| **2. Generic core primitive** | No domain-specific type fits, but raw primitive is still banned | `Safe_Str`, `Safe_Int`, `Safe_UInt`, `Safe_Float` |
| **3. Custom Safe_Str / Safe_Int subclass** | A genuinely different regex / range / length needs enforcing **and** you can write a real test that catches the difference | `Safe_Str__Image_Tag` (registry/namespace/name:tag@digest), `Safe_Str__Image_Digest` (sha256:64hex) |

**Climb-the-ladder discipline:**

1. Start at Level 1 - look for an existing primitive in the catalogue
   (v3.28.0 has the full list). At least 70% of cases are covered.
2. If none fits, drop to Level 2 - use the generic `Safe_Str` / `Safe_Int` etc.
3. **Only** climb to Level 3 if you can articulate the validation rule
   AND write a failing test that the generic primitive wouldn't catch.

If creating a Level-3 type, document the regex / range inline and link to
a test that exercises the boundary.

## Closed-set values: prefer Enum / Literal, not Safe_Str__X

The pack's instinct on something like "provider name must be one of
docker, podman, buildah, oci-img-tool" is sometimes to model it as
`Safe_Str__Provider_Name`. That's the wrong shape - it's a **closed
set**, and the right tool is `Enum` or `Literal`:

```python
# ✗ Over-engineered - custom Safe_Str regex enumerates the values implicitly
class Safe_Str__Provider_Name(Safe_Str):
    regex = re.compile(r'^(docker|podman|buildah|oci-img-tool)$')

# ✓ Right shape - the set is closed and meaningful
class Enum__Provider_Name(str, Enum):
    DOCKER         = "docker"
    PODMAN         = "podman"
    BUILDAH        = "buildah"
    OCI_IMG_TOOL   = "oci-img-tool"

# ✓ Or for very small sets, inline Literal
class Schema__Provider_Config(Type_Safe):
    kind: Literal["docker", "podman", "buildah", "oci-img-tool"]
```

Enums give you IDE auto-complete, exhaustive switch checking via mypy,
and JSON round-tripping for free (Type_Safe handles enum serialisation
- v3.63.4 §"Enum Support").

## M1 schema mapping (provisional)

These are the schemas M1 will introduce. Mapping each field to the
calibrated level **before** writing code so the review catches over-typing
early:

### Schema__Provider_Config (the provider abstraction)

| Field | Proposed type | Level | Rationale |
|-------|--------------|-------|-----------|
| `kind` | `Enum__Provider_Kind` | Enum | Closed set |
| `binary_path` | `Safe_Str__File__Path` | L1 | existing primitive fits |
| `binary_version` | `Safe_Str__Version` | L1 | existing primitive fits |
| `registry_url` | `Safe_Str__Url = None` | L1 | optional, existing fits |
| `credentials_ref` | `Safe_Str__Key = None` | L1 | optional vault key reference |
| `extra_args` | `List[Safe_Str]` | L2 | free-form CLI args, generic Safe_Str is enough |

### Schema__Exit_Code (the exit code registry)

| Field | Proposed type | Level | Rationale |
|-------|--------------|-------|-----------|
| `code` | `Enum__Exit_Code` | Enum | Closed set; numeric values are the enum's `.value` |
| `name` | (the enum's `.name`) | - | Don't denormalise |
| `description` | `Safe_Str__Text` | L1 | human-readable |

So the registry **is** an `Enum`. No `Safe_UInt__Exit_Code` subclass.

### Schema__Spec_Ref (spec identifier)

| Field | Proposed type | Level | Rationale |
|-------|--------------|-------|-----------|
| `spec_id` | `Safe_Str__Id` | L1 | generic existing identifier |
| `version` | `Safe_Str__Version` | L1 | existing fits |
| `display_name` | `Safe_Str__Display_Name = ''` | L1 | optional |

No `Safe_Str__Spec_Id` subclass until we see a real validation rule we
need to enforce.

### Schema__Image_Ref (the only place L3 is justified so far)

| Field | Proposed type | Level | Rationale |
|-------|--------------|-------|-----------|
| `registry` | `Safe_Str__Url = None` | L1 | optional |
| `repository` | `Safe_Str__Slug` | L1 | url-friendly |
| `tag` | `Safe_Str__Image_Tag` | **L3** | OCI tag has its own grammar (`[a-zA-Z0-9_][a-zA-Z0-9._-]{0,127}`); existing primitives don't capture this |
| `digest` | `Safe_Str__Image_Digest = None` | **L3** | `sha256:<64-hex>` shape; `Safe_Str__SHA1` is 40-hex so doesn't fit |

These two L3 types **earn their existence** because they have non-trivial
regexes and the OCI/Docker spec defines them precisely.

### Schema__Build_Result, Schema__Layer_Spec, Schema__Workspace

Defer the field-level mapping until M2/M3 - same ladder will apply.

## Side-effects on coding style

A few extras lifted from the testing guidance (v3.1.1) that affect M1
test code:

- Test files mirror source structure under `sg_image_builder__tests/unit/`
- No docstrings in tests; use end-of-line inline comments for alignment
- Use the `with Schema__X() as _:` pattern + `_.obj() == __(...)` for state assertions
- Use `__SKIP__` for auto-generated IDs / timestamps in `.obj()` comparisons
- One test method per source method; `test__init__` is mandatory

From the decorator guide (v3.63.3):

- `@type_safe` on public APIs of provider classes; skip for private helpers
- No `Optional[T]` - use `param: T = None` instead, and return `None` for "not found"
- No explicit `str()` casts on `Safe_*` instances - Type_Safe auto-converts
- No raw `{}` / `[]` literals when a `Dict__X` / `List__X` subclass exists

## Addendum (12 May 2026, after M1 PR1)

PR1 surfaced a refinement to the L3 trigger criterion. Original wording:

> Climb to L3 only if you can articulate the validation rule AND write a
> failing test that the generic primitive wouldn't catch.

Add a second trigger - the **silent transformation** failure mode:

> Also climb to L3 if the L1/L2 primitive **silently transforms** the input
> (REPLACE-mode regex, `trim_whitespace=True`, etc.) in a way that loses
> correctness for the domain.

**Why:** PR1's smoke test found two real cases where assumed-fine L1 primitives
silently corrupted data:

- `Safe_Str__Text` (regex `[^a-zA-Z0-9_ ()\[\]\-+=:;,.?*\'"]` REPLACE) turns
  `library/ubuntu` -> `library_ubuntu`. Strips slashes from OCI repo names
  and from shell commands.
- `Safe_Str__Http__Text` (`trim_whitespace=True`) drops trailing newlines
  from `stdout='Linux ...\n'`. POSIX convention says the trailing newline
  carries meaning.

Practical guidance: when picking an L1 primitive, inspect three attributes:

- `regex` — what chars does it claim to filter?
- `regex_mode` — `REPLACE` is the silent-failure mode; `MATCH` + `strict_validation=True` is the loud-failure mode
- `trim_whitespace` — `True` drops leading/trailing whitespace

If any of those would lose correctness for the target domain, jump to L3
even if the existing primitive "looks right". The M1 PR1 review documents
the two L3 additions this prompted (`Safe_Str__Image_Repository`,
`Safe_Str__Process__Text`).
