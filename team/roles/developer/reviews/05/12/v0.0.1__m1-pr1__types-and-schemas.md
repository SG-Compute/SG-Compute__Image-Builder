## Delta vs. the M1 plan in the calibration review

The 11-May calibration review listed **two** L3 primitives for M1 (Image_Tag,
Image_Digest). Two more L3 types earned their existence during PR1 smoke
testing because the assumed L1 fits turned out to silently corrupt data:

### `Safe_Str__Image_Repository` (new L3)

The plan assumed `Safe_Str__Text` for `repository`. Smoke test result:

```
input:  Schema__Image_Ref(repository='library/ubuntu')
output: repository == 'library_ubuntu'           # `/` silently replaced with `_`
```

`Safe_Str__Text` has regex `[^a-zA-Z0-9_ ()\[\]\-+=:;,.?*\'"]` in REPLACE
mode - it strips `/`. For OCI repository names where `/` is the path
separator (`library/ubuntu`, `org/sub/app`), this loses correctness.

The L3 type encodes the actual OCI distribution-spec grammar:
`[a-z0-9]+(?:(?:[._]|__|-+)[a-z0-9]+)*(?:/[a-z0-9]+(?:(?:[._]|__|-+)[a-z0-9]+)*)*$`
in MATCH mode with `strict_validation=True`, so non-OCI inputs **fail
loudly** instead of being silently mangled.

### `Safe_Str__Process__Text` (new L3)

The plan assumed `Safe_Str__Http__Text` for `stdout` / `stderr` / `command`.
Smoke test result:

```
input:  Schema__Exec__Result(stdout='Linux ...\n')
output: stdout == 'Linux ...'                    # trailing \n silently dropped
```

`Safe_Str__Http__Text` has `trim_whitespace=True`, which silently drops
trailing newlines. For exec capture where the trailing newline carries
meaning (POSIX text-file convention), that's data loss.

The L3 type inherits from `Safe_Str__Http__Text` to keep its sensible
control-char filtering, then overrides:

- `max_length = 10 * 1024 * 1024` (1 MB is too small for real build output)
- `trim_whitespace = False` (preserve exec output verbatim)

We also discovered that `Safe_Str__Text` strips `/` and quotes, mangling
shell commands like `/usr/bin/ls -la "x"`. Same L3 type is used for the
`command` field for the same reason.

## Methodology takeaway for the calibration review

The four-level ladder in v0.0.1__type-safe-usage-calibration.md says:

> Climb to L3 only if you can articulate the validation rule AND write a
> failing test that the generic primitive wouldn't catch.

PR1 produced **two new pieces of evidence** that should refine the rule:

> Climb to L3 also if the L1/L2 primitive **silently transforms** the input
> (REPLACE-mode regex, `trim_whitespace=True`, etc.) in a way that loses
> correctness for the domain.

Updated mental model: when picking an L1 primitive, inspect its
`regex_mode`, `trim_whitespace`, and `regex` defaults - REPLACE mode is
the silent failure mode that the L1 catalogue hides behind a friendly name.
Both `Safe_Str__Text` and `Safe_Str__Http__Text` are REPLACE-mode and
silently strip; only MATCH-mode strict primitives surface bad input.

I'll re-roll this into the next revision of the calibration review.

## Type_Safe behaviour findings (worth remembering)

1. **`allow_empty=False` blocks auto-init.** A schema field of a Safe_Str
   subclass with `allow_empty=False` and no `= default` makes
   `Schema__X()` raise on construction (auto-init tries to build the
   primitive with no value). Two ways out:
   - Provide a sensible default: `tag: Safe_Str__Image_Tag = 'latest'`
   - Set `allow_empty=True` on the type so `''` is the "not yet set"
     sentinel: did this for `Safe_Str__Image_Repository`. Non-empty
     values still get validated against the regex.

2. **mypy can't see Type_Safe's auto-conversion.** The canonical
   `version: Safe_Str__Version = '1.0.0'` pattern produces
   `error: Incompatible types in assignment`. Resolved with narrow
   `# type: ignore[assignment]` on the two affected lines in
   `Schema__Image_Ref` (rather than disabling the error globally, which
   would mask real type bugs).

3. **CRLF normalisation.** `Safe_Str__Http__Text` (and our `Process__Text`
   that inherits from it) converts `\r\n` → `\n`. Acceptable for captured
   subprocess output; explicitly tested in
   `test_Safe_Str__Process__Text.test__normalises_crlf_to_lf`.
